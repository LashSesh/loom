# 17 — MESSLATTE „PARITY, THEN SURPASS" (Operationalisierung des Auftraggeber-Maßstabs)

**§0 Der Maßstab (wörtlich vom Auftraggeber):** Das System ist erst dann auch nur ein fertiger *Prototyp*, wenn es vollfunktionale Systeme wie Claude Code (Opus), GitHub Copilot, Cursor oder Bolt **mehrfach übertroffen** hat. Diese Karte operationalisiert ausschließlich diesen Satz. Sie behauptet keinen weiteren Zweck; der Zielattraktor bleibt beim Auftraggeber. Jedes frühere „vollständig" ist ab jetzt zu lesen als: **Fundament vollständig — Wettbewerbs-Prototyp bei null.**

## §1 Ehrlicher Standort an diesem Maßstab

| Fähigkeit | Jene Systeme | CCE heute | Befund |
|---|---|---|---|
| Frontier-Modell produktiv | ja | Stub/Mocks hinter fertigem Gateway | **fehlt** |
| Agentisches Arbeiten auf echten Repos | ja | Tore/Locks spezifiziert+getestet, nie real gefahren | **fehlt** |
| Live-Weltzugang im Alltag | ja | ein eingefrorener, belegter Abruf | **fehlt** |
| Täglich benutzbare Oberfläche | ja | gebaut, host-blockiert, unbenutzt | **fehlt** |
| Beweis je Ergebnis, Replay-Identität, versiegelte Egress-Tore, sichtbare Residuen, zertifizierbares Format, Gedächtnis aus Bewiesenem | **nein — strukturell keines** | vollständig, testbewacht | **Alleinstellung** |

## §2 Die sechs Disziplinen, in denen „übertreffen" messbar wird

**D1 Nachweisbarkeit** (jedes Ergebnis trägt Beweis + Replay — Gegner können strukturell nicht antreten) · **D2 Wiederholbarkeit** (gleicher Auftrag ⇒ gleiche Klasse, maschinell geprüft) · **D3 Governance** (kein Egress ohne Tor, nachweisbar; kein stilles Scheitern) · **D4 Aufgabenparität** (identische Coding-/Dokument-/Rechercheaufgaben: Ergebnisqualität ≥ Gegner) · **D5 Autonomie unter Gates** (lange Auftragsketten ohne Menschenkorrektur, aber mit Menschenhoheit) · **D6 Auditierbarkeit** (der gesamte Arbeitsweg als prüfbarer `.loom`-Körper). **Definition „mehrfach übertroffen":** kategorische Überlegenheit in D1/D2/D3/D6 (die Gegner können dort nicht antreten) **UND** belegte Parität-bis-Überlegenheit in D4/D5 für definierte Aufgabenklassen. Beides zusammen, sonst gilt der Prototyp als nicht fertig.

## §3 Etappen zum Prototyp (nach X4)

**P1 · Frontier-Intelligenz real:** erster echter CloudModelProvider = Anthropic-API hinter dem **unveränderten** Gateway (Manifest, PromptContext-/Privacy-/Budget-Gates, recorded-Replay). Benötigt die einzige Entscheidung, die nur der Auftraggeber treffen kann: Freigabe + API-Schlüssel (als Secret der Agent-Umgebung; nie im Repo). Damit löst sich zugleich der GGUF-Teil der Host-Leiste. **P2 · SWE-Tiefe:** die Software-Familie von PL3-Struktur auf Arbeitsreife: Repo-Workbody (Code-Einheiten, Diffs als Artefakte, Build/Test-Läufe als Evidence), Tool-Klassen fs/git/build/test real unter ToolCapabilityLocks. **P3 · Dogfooding-Meilenstein (der Prototyp-Kerntest):** CCE führt einen echten, kleinen Bauauftrag **am eigenen Repository** aus — Wunsch → Frontier-Kanzel formt → Plan → ToolGateway-Ausführung → Gates → PhaseBlocks → Replay → zertifizierter Ergebnis-Workbody. *Der Moment, in dem CCE Claude Code in unserem eigenen Entwicklungs-Loop ersetzt.* **P4 · Vergleichsläufe:** identische Aufgabenpakete in CCE vs. Claude Code/Cursor; Ergebnisse, Zeiten, Fehlerbilder und Beweislage als `.loom`-Benchmark-Körper — die Überlegenheitsbehauptung wird selbst ein zertifiziertes Artefakt.

## §4 Neue Abnahme-Klasse K9 · CompetitiveDoD

`PrototypFertig (im Sinne des Auftraggebers) = 1 ⟺ P3 bestanden ∧ D1–D6-Matrix dokumentiert ∧ mindestens eine Aufgabenklasse mit belegter Überlegenheit in D4/D5 ∧ kategorische D1/D2/D3/D6-Nachweise als Benchmark-Workbodies.` Kein „fertig" mehr ohne diese Klasse; alle früheren DoD-Klassen K1–K8 sind ihr Fundament, nicht ihr Ersatz.

## §5 Reihenfolge

X4 (Fundament-Schlussstein R-CYC-1 — wird später selbst Benchmark-Disziplin D2/D6) → P1 → P2 → P3 → P4. Host-Leiste: durch P1 teilaufgelöst; Rest (Drei-OS, Glyphen-Desktop) bleibt am Host-Termin.
